# Splito logic audit, commit c74a553 (2026-10-27)

This audit was read-only and ran in a detached worktree at c74a553. Probes ran with bun against `packages/domain` and `packages/sync`, using an in-memory SQL store. I read the client findings in the source.

## Summary

| Rejected, or a sub-claim corrected | 4 |

**Themes**
1. **Amounts in 3-decimal currencies (BHD, KWD, OMR)** go wrong whenever text the app wrote itself is parsed back in a comma locale. This is the only path to a silent 1000x money error, and it is web only. On native, the Intl polyfill reads de-DE as en, so the mark is always `.`.
2. **The rules for many currencies at once are only half built.** No demo group holds two currencies. Record payment is locked to INR. The sidebar shows one currency per group. The cash-rounding unit is shared by every currency. Picking a group overwrites the expense currency.
3. **Timezone and number-format preferences are only partly wired in:** payments, Activity, dates and the native number format ignore them.

## Critical

### C1. Prefilled Record payment / Call it even amount is read back 1000x for BHD/KWD/OMR in comma locales
- **Area:** Settle up, Record payment, Call it even
- **File:** `apps/client/src/components/people/RecordPaymentDialog.tsx:135-138`, `apps/client/src/features/settlement/CallItEvenDialog.tsx:109-112`, parsed by `components/people/ledger.ts:136-147` and `packages/domain/src/calc.ts:89-98`
- **Scenario:** Web, number locale de-DE or fr-FR. The open balance is BHD 1.234 (1234n). The prefill is `toDecimalString(1234n, 3)`, which gives `"1.234"` with a `.`. `parseTypedAmount` reads it with the mark `,`, sees `.` plus 3 digits, and treats it as grouping, so the result is 1234000n (BD 1,234.000). If you tap Record payment as offered, it saves a payment 1000x too large. In Call it even, the same prefill comes out larger than the balance, so Save stays disabled.
- **Evidence (probe):** `prefill 1.234` -> `evaluateAmount('1.234','BHD',',')` = `1234000`. `'7.500','KWD',','` = `7500000`. 2-decimal currencies come out right (`'12.50','EUR',','` = `1250`).
- **Fix:** Write the prefill with the locale's own mark: `toDecimalString(...).replace('.', decimalMark(locale))`. Or keep the bigint until the user edits the field. Add a round-trip test for scales 0, 2 and 3 under both marks.

### C2. Editing a 3-decimal-currency expense in a comma locale multiplies it by 1000; in a `.` locale it cannot be saved
- **Area:** Expense composer, edit
- **File:** `apps/client/src/components/split/form.ts:159` (`money()`), `:173-193` (`formFromExpense`), `:331-336` and `:312-326` (`evaluateForm`)
- **Scenario:** A BHD 12.345 expense. `formFromExpense` sets `amount: "12.345"`, and fills `paid`, `exact` and other rows the same way, always with `.`. In de-DE, `evaluateForm` reads 12,345.000. The form is valid, so changing only the title and saving stores a total and shares 1000x too large. In en-US or en-IN the main amount throws AMBIGUOUS_AMOUNT. There is a picker for that, but picking "grouped" by mistake also gives 1000x, and rows such as `"5.000"` have no picker at all (see M3).
- **Evidence (probe):** `evaluateAmount('12.345','BHD','.')` gives AMBIGUOUS_AMOUNT. The same shape with `,` gives x1000 (see C1).
- **Fix:** Pass the decimal mark into `formFromExpense` and write every money string with it, or set `amountReading: 'decimal'` and a matching row reading. Add a round-trip test, `evaluateForm(formFromExpense(e)).total === e.total`, for JPY, INR and BHD under both marks.

## Major

### M1. Amount parser: a repeated decimal mark is still read as the decimal point (KWD 1.000.000 becomes KD 1,000)
- **Area:** smart amount parser, `plainNumber`
- **File:** `packages/domain/src/calc.ts:89-98`
- **Scenario:** `evaluateAmount('1.000.000','KWD','.')` = 1000000n (KD 1,000.000, not KD 1,000,000). `'1,000,000','OMR',','` and `'1.234.567','BHD','.'` behave the same. `'1.2.3'` in USD gives $12.30, and `'12,34,56'` in INR gives ₹1,234.56, with no error in either case.
- **Evidence (probe):** `1.000.000 KWD . => 1000000`, `1.2.3 USD . => 1230`, `12,34,56 INR . => 123456`.
- **Fix:** A mark can only be decimal when it appears once (`num.indexOf(num[last]) === last`). Otherwise treat it as grouping, or throw INVALID_AMOUNT.

### M2. Amount parser: for JPY, KRW and VND, a non-locale mark followed by 1-2 digits is read as grouping (2.5k JPY becomes ¥25,000)
- **Area:** smart amount parser, scale-0 currencies (2 reviewer findings merged)
- **File:** `packages/domain/src/calc.ts:93-95`
- **Scenario:** With scale 0, `tail.length <= scale` is never true, so every mark that is not the locale's own gets stripped. In de-DE, `'2.5k'` JPY gives ¥25,000 while the same input in EUR gives €2,500. `'2.5'` JPY gives ¥25 instead of TOO_MANY_DECIMALS, and `'1.5L'` gives ¥1,500,000. In en-US, `'1,5'` gives ¥15 and `'1,5k'` gives ¥15,000, while INR gives ₹1,500.
- **Evidence (probe):** `2.5k JPY , => 25000`, `2.5 JPY , => 25`, `1.5L JPY , => 1500000`, `1,5 JPY . => 15`, `1,5k INR . => 150000` vs `1,5k JPY . => 15000`.
- **Fix:** A 1-2 digit tail is never a thousands group. Treat it as decimal whatever the scale (`tail.length !== 3`), and let parseAmount or the shorthand divisibility check raise TOO_MANY_DECIMALS.

### M3. Split rows with 3 decimals can never be entered in `.` locales
- **Area:** Expense composer, exact / paid / adjusted / items rows
- **File:** `apps/client/src/components/split/form.ts:312-326` (`rowAmount` passes no `reading`)
- **Scenario:** en-US or en-IN, BHD total 10.001, exact rows `5.001` and `5.000`. Each row throws AMBIGUOUS_AMOUNT, the form error is INVALID_ROW_AMOUNT, and there is no picker on rows (only the main amount gets "Did you mean"). The edit form writes `"5.000"`, so these rows cannot be saved either.
- **Evidence (probe):** `evaluateAmount('5.001','BHD','.')` gives AMBIGUOUS_AMOUNT. The picker exists only at `ExpenseComposer.tsx:494-496`.
- **Fix:** Rows call `evaluateAmount` with `reading: 'decimal'`, which is safe because the keypad never types grouping marks. Or give each row a reading picker.

### M4. Restoring from Recently deleted brings back expenses and payments that point to a deleted person
- **Area:** mutations, restore (2 findings merged)
- **File:** `packages/sync/src/mutations.ts:249-255` (`restore`), `:149-159` (`deletePerson` checks only live records)
- **Scenario:** An EUR 30 expense split with Bob, plus Bob paying EUR 5. Delete both, then delete Bob, which is allowed. Restore both. They are live again and point to the tombstoned Bob. The open EUR 10 balance cannot be settled (`createRepayment` throws UNKNOWN_PERSON) or edited (`updateExpense` throws UNKNOWN_PERSON), and Bob is not in People.
- **Evidence (probe):** `person deleted true expense live true`, `balances [{"person":"id2","groupId":null,"currency":"EUR","amount":"1000"}]`.
- **Fix:** In `restore`, run the checks create runs: `requireLive` on every payer, share person, from and to (UNKNOWN_PERSON), plus the group. Or have `deletePerson` also count bin items that have not been purged.

### M5. Picking a group silently overwrites the expense currency and keeps the typed number (€45 becomes ₹45), in edit mode too
- **Area:** Expense composer, group picker
- **File:** `apps/client/src/components/split/ExpenseComposer.tsx:178-202` (line 193 `currency: g.data.currency`, line 197 `excluded: []`)
- **Scenario:** Edit a €45 expense in an INR-home group and re-pick that group, or switch to another INR group. The currency becomes INR, the amount text stays `45.00`, and Save stores ₹45. In Add mode, a currency the user picked first is overwritten too. People the user had unticked come back into the split. This breaks §26.13, where the home currency only pre-fills new expenses.
- **Fix:** Change the currency only in Add mode, and only while it is still the untouched pre-fill (track `isCurrencyPicked`). Never change it in edit mode. Keep exclusions for people who are still in the split.

### M6. Unticking yourself in "Split with" silently makes someone else the payer
- **Area:** Expense composer, Split with
- **File:** `apps/client/src/components/split/ExpenseComposer.tsx:160-176` (line 169), PeopleDialog at `:372-384` gets no `lockedIds`
- **Scenario:** I paid ₹900 with Riya and Sam, then untick myself. `payer` becomes `next[0]` = Riya. The save records Riya paying ₹900, Sam owing Riya ₹450, and nobody owing me anything.
- **Fix:** Pass `lockedIds={[form.payer]}`, or the payers in multi-payer mode, to PeopleDialog. Or move the payer to `excluded` instead of dropping them.

### M7. Percent inputs refuse the comma decimal mark
- **Area:** Split editor, percent mode / itemize % charges
- **File:** `packages/domain/src/calc.ts:219-227` (`parseBasisPoints`), called at `apps/client/src/components/split/form.ts:426,490`
- **Scenario:** In de-DE, `12,5` % service or `33,33` % gives INVALID_PERCENT, so only whole percentages can be entered.
- **Evidence (probe):** `bp 33,33 THROW INVALID_PERCENT`, `bp 12,5 THROW INVALID_PERCENT`.
- **Fix:** Normalise `,` to `.` (a percent has no grouping), or pass the decimal mark in.

### M8. Record payment on a friend's page is locked to INR, or to the open currencies
- **Area:** Person, Record payment
- **File:** `apps/client/src/screens/Person/index.tsx:222` (`openCurrencies[0] ?? 'INR'`), `:505-517` (`currencies` undefined when fewer than 2 are open)
- **Scenario:** A user with default currency EUR who is settled with Sam taps Record payment and can only record INR. With EUR as the only open currency, an INR payment cannot be recorded. §26.13 says any repayment can use any currency.
- **Fix:** Fall back to the `defaultCurrency` preference, and offer CurrencyDialog when the wanted currency is not open.

### M9. Payments and write-offs are dated in the device timezone, not the Timezone preference that expenses use
- **Area:** dates (2 findings merged)
- **File:** `apps/client/src/components/people/ledger.ts:118-128` (`todayLocal`), used at `RecordPaymentDialog.tsx:190` and `CallItEvenDialog.tsx:175`. Expenses use `useExpenseTz()` (`components/split/shared.tsx:23-26`).
- **Scenario:** The device is in America/Los_Angeles and the preference is Asia/Kolkata. At 2026-10-26 20:00 PDT an expense is dated 2026-10-27 (Asia/Kolkata). A payment one minute later is dated 2026-10-26 (America/Los_Angeles), the day before the debt it settles. At a month edge it lands in a different Analytics month.
- **Fix:** `localToday(useExpenseTz())` / `useTimeZone()`, and delete the device-only helper.

### M10. Home nets a friend's direct and group balances, so open debts show as "Settled"
- **Area:** People overview
- **File:** `apps/client/src/screens/People/index.tsx:82-117` (uses `personSummary(...).total`), `packages/domain/src/ledger.ts:208-220, 263-275`
- **Scenario:** Bob owes me ₹10 directly, and I owe Bob ₹10 in group G. Bob's INR total is 0. The overview shows "₹0.00" owed and owe, Bob counts as "settled", and the row shows a Settled pill. On the Person page, `hasOpenBalance` is false, so Call it even is hidden. Meanwhile Groups and the Group page say "You owe ₹10". This contradicts the spec's non-goal of netting across groups (spec line 42) and `groupTotals`' own comment ("never settled").
- **Evidence:** `balanceTotals` sums `p.byCurrency[c].total`, where `total` = direct + every group.
- **Fix:** Work out owed and owe per part (direct and each group), as `groupTotals` does. "Settled" should mean every part is zero.

### M11. With infeasible payment rules, Group Balances shows no pairs while People shows pairs from a fallback plan
- **Area:** Group page vs People
- **File:** `apps/client/src/screens/Group/index.tsx:219-224` (`infeasible` gives `[]`), `packages/domain/src/ledger.ts:139-141` (`balanceRows` falls back to NO_RULES)
- **Scenario:** The rules are `{allowListOnly: true, edges: {}}` (allowed by `updateGroupRules`). I pay 300 for me, a and b. The Group Balances tab shows no "who owes whom" and Settle up is stuck, but People says "a owes you 100 in G". This breaks the invariant stated in `components/groups/net.ts`.
- **Fix:** Use one policy everywhere: show the fallback on Group Balances with an "outside your rules" note, or drop the fallback in `balanceRows`.

### M12. "Recently active groups" shows only one currency of a group with balances in several
- **Area:** desktop right column
- **File:** `apps/client/src/view/shell/desktop/LeftNav.tsx:560-563`
- **Scenario:** Lisbon: I am owed €45 and I owe ₹1,200. Only `+€45` shows (the first currency alphabetically), and the accessibility label leaves out the ₹ debt. This breaks §26.13 ("shown per currency, side by side").
- **Fix:** One chip per open currency, as GroupRow does. Put every currency in the label.

### M13. Demo data breaks §26.13: no group has two currencies, and there are no 0- or 3-decimal currencies
- **Area:** demo data (2 findings merged). This is the user's explicit request.
- **File:** `apps/client/src/data/demoData.ts:23` (`currency: 'INR' | 'EUR'`), `:101-150`
- **Scenario:** Every Goa and Flat expense is INR and every Lisbon expense is EUR. Riya, Arjun and Priya only share INR, Lena and Diego only EUR, and Sam alone has two. There is no JPY, BHD or KWD, and no large set (commit c74a553 changed only `docs/ARCHITECTURE.md`; the large set sits on unmerged `feat/demo-large`). So no screen ever shows a group with more than one currency, which is also how C1, C2, M2, M3 and M12 went unseen.
- **Fix:** Widen the type to CurrencyCode. Add INR expenses to Lisbon (for example a flight booked from India) and EUR or USD to Goa. Give Riya and Priya a second currency. Add one JPY expense, one BHD or KWD expense, and a repayment in a second currency. Land the large set. Recompute the e2e expectations.

### M14. Amount search only understands en-US number formats
- **Area:** search
- **File:** `packages/sync/src/search.ts:56` (NUMBER), `:78-82`
- **Scenario:** `1,00,000` (en-IN) is split into the words `1`, `00`, `000`, so the ₹1,00,000 rent is not found. `1.000` (de-DE) becomes amount `1.000` = 1, so it matches €1 and not €1,000. `1.234,56` is split into words and finds nothing.
- **Evidence (probe):** `parseSearchQuery('1,00,000')` gives 3 text tokens, `'1.000'` gives `{amount:"1.000"}`, and `'1.234,56'` gives 3 text tokens.
- **Fix:** Parse with the active number locale (the same parser as the amount input). Also accept Indian 2-digit grouping and `d.ddd,dd`.

### M15. The cash-rounding unit is one account-wide number of whole units, applied to every currency
- **Area:** split, cash rounding
- **File:** `packages/sync/src/preferences.ts:97-99`, `apps/client/src/components/split/form.ts:380`, `packages/domain/src/allocate.ts:50-70`
- **Scenario:** Cash rounding is opt-in (`split.roundCash` defaults to false). Once it is on, `roundTo=100` (meant as ₹100) splits a €45 dinner for 3 into a: €45, b: 0, c: 0. `roundTo=10` gives €20 / €15 / €10, and for KWD every share rounds to KD 10.
- **Evidence (probe):** `allocateCash(4500n, 3 equal, cashUnit('EUR',100))` = `{a:4500,b:0,c:0}`. With `cashUnit('EUR',10)` it is `{a:2000,b:1500,c:1000}`.
- **Fix:** Keep `roundTo` per currency, or scale it per currency. In `allocateCash`, skip rounding when `total/unit` is less than the number of participants.

### M16. On web, Back fallbacks never run after a deep link or refresh
- **Area:** navigation
- **File:** `apps/client/src/navigation/linking.web.ts:27-35` (`initialRouteName: 'People'`), `navigation/goBack.ts:18-40`
- **Scenario:** Open `/groups/g1/settle` directly and press Back: you land on People, not Group g1. `/groups/g1` goes to People instead of Groups, and `/expense/e1/edit` close goes to People instead of the Expense. `canGoBack()` is always true, so `backFallback` is dead code (§3, A-014).
- **Fix:** Override `getStateFromPath` to put `backFallback(leaf)` under the leaf, and keep People under the Add-expense dialog only.

### M17. On native, the Number format preference and en-IN devices fall back to plain `en` grouping
- **Area:** i18n polyfill
- **File:** `apps/client/src/locale/i18n.ts:7-13` (data only for `en` and `hi`)
- **Scenario:** With Number format set to European or Indian on iOS/Android, amounts still show `₹1,234,567.50`, and an en-IN device gets Western grouping (§26.2). `decimalMark('de-DE')` returns `.` on native.
- **Fix:** Import the numberformat and pluralrules locale data for `en-IN`, `de` and `fr`, and test every `PREFS.numberLocale` option under the polyfill.

### M18. The Date format preference only affects Search
- **Area:** preferences wiring
- **File:** `apps/client/src/locale/useDates.ts:16-20` (`useFormatLocalDate`, used only in `screens/Search/index.tsx`)
- **Scenario:** With Year first (ymd), Search shows `2026-10-26`, while the Expense screen (`Expense/index.tsx:278`), Person history (`HistoryRow.tsx:284`), the Group page, Analytics, Restore and the composer all use `i18n.date`.
- **Fix:** Send every LocalDate display through one hook that reads `dateFormat`.
